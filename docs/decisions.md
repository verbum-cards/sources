### ADR-13. Локальное хранилище на устройстве

**Контекст.** T1.4 требовал схему локальной SQLite-базы для пользовательских данных и пакета словаря. Нужно было решить: смешивать ли контент словаря и пользовательские данные в одном файле (с `ATTACH`/JOIN), и как типизировать растущее число контрактов между mobile и будущим `apps/api`.

**Варианты.**
1. Один файл SQLite с `ATTACH` пакета словаря к пользовательской базе и JOIN при чтении карточки.
2. Два файла без JOIN, содержимое карточки — снимок в пользовательской базе (выбрано).
3. Контракты — обычные TS-интерфейсы (`interface`) без рантайм-валидации (исходная рекомендация архитектора — отложить Zod до появления API).
4. Контракты — Zod-схемы с первого дня, тип выводится через `z.infer` (выбрано владельцем продукта явно, вопреки исходной рекомендации).

**Решение.** Два независимых файла: `cards-user.db` (пользовательские данные, миграции по `PRAGMA user_version`, только вперёд) и `dictionary-<lang>-<native>.db` (общий контент, только чтение, версия формата в `PRAGMA user_version`/`pack_meta.schema_version`, версия контента в `pack_meta.content_version`, миграций нет — заменяется целиком или дельтой). Между файлами нет `ATTACH`/JOIN: всё, что рисуется на карточке (лемма, перевод, пример), хранится снимком в `card_content` внутри пользовательской базы. Кеш FSRS (`card_schedule`) и исходящая очередь операций синхронизации (`sync_op`) — отдельные локальные таблицы, не смешанные с синхронизируемыми полями и не описанные в `@cards/contracts`. Каждый экспортируемый тип `@cards/contracts` — Zod-схема (`XSchema`) плюс тип, выведенный через `z.infer<typeof XSchema>`; подключено сразу в T1.4, не отложено до API.

**Последствия.**
- Сессия и главный экран работают одним файлом (`cards-user.db`) независимо от версии и наличия пакета словаря — если пакет ещё не скачан или устарел, уже добавленные карточки не ломаются.
- Контент карточки не обновляется автоматически при обновлении пакета словаря — обновление `card_content` (`source`, `content_version`) остаётся отдельной задачей (вне T1.4).
- Контракты валидируют данные в рантайме и типизируют одновременно — меньше риска, что серверная валидация и клиентские типы разойдутся; цена — Zod как рантайм-зависимость `@cards/contracts` уже сейчас, до появления самого API.
- Выход из аккаунта (флоу F21, вне области T1.4) не должен молча удалять `cards-user.db`: перед физическим удалением локальной базы нужен запрос подтверждения пользователю — это ограничение зафиксировано здесь и должно быть учтено при реализации экрана выхода.

**Связано.** ADR-3 (local-first), ADR-4 (синхронизация по журналу операций), ADR-7 (CEFR у значения). Найденные противоречия `docs/sync-protocol.md` (entity_id для `user_profile`/`user_deck`, `kind=delete` для `review_log`, `deck.type=user` и т.п.) — предмет T1.5, не этого решения.

### ADR-14. Протокол синхронизации v1

**Контекст.** `docs/sync-protocol.md` писался как черновик v0 до схемы базы. Ревью T1.5 сверило документ с реальными контрактами (`packages/contracts/src/{sync,user}.ts`) и схемой `apps/mobile/src/db/migrations/001_init.ts` и нашло семь известных нестыковок с моделью данных плюс семь новых вопросов, четыре из которых меняли бы объём работ недель 5–7 уже после начала реализации.

**Варианты по спорным местам и что выбрано.**
1. Состояние карточки: синхронизировать `state` целиком — тогда каждое повторение порождает операцию по карточке и конфликт по полю, которое на обоих устройствах и так пересчитывается из журнала. Выбрано: синхронизируется только намерение пользователя `status` (`active` / `suspended` / `known`), фазы `new` / `learning` / `review` — производные от `card_schedule` и журнала.
2. Слияние дублей: (а) новое поле `mergedIntoCardId`; (б) перенос записей журнала на победителя; (в) надгробие без учёта истории. (б) нарушает неизменяемость журнала или раздувает его копиями, (в) молча отменяет обещание «журналы объединяются» и ухудшает планирование. Выбрано (а).
3. Профиль при объединении аккаунтов: по полю или записью целиком. Выбрано: локальный профиль побеждает целиком — пользователь только что прошёл онбординг на этом устройстве, а смесь «родной язык с одного устройства, изучаемый с другого» бессмысленна.
4. Формат идентификаторов и дат в Zod: оставить `z.string()` или ужесточить. Выбрано: `z.uuid()` и `z.iso.datetime()` — граница синхронизации это внешняя граница, а `z.iso.datetime()` по умолчанию требует `Z` и запрещает смещение, то есть закрепляет уже принятый формат «UTC плюс отдельный `tz_offset_min`».

**Решение.** Зафиксировано в `docs/sync-protocol.md` (v1). Уточняет ADR-13 в двух местах: метаданные конфликтов (`field_meta` / `field_revisions`) остаются локальными и не становятся полем контракта, а состояние карточки делится на синхронизируемое намерение `status` и производную фазу — то есть схема из T1.4 требует миграции 002. Ключевое: `entityId` задан по сущностям (`card.id`, `review_log.id`, `userId`, `deckId`); конфликты разрешаются по полю через `field_revisions` — это метаданные, а не поле контракта, и через журнал они не едут; `review_log` допускает только `kind = 'create'`, удаление карточки её журнал не стирает; операции делятся на `create` / `upsert` / `delete`, `itemType` / `itemId` / `createdAt` неизменяемы после создания; курсор двигает только pull, ответ на push курсора не содержит; `userId` сервер берёт из токена, а не из тела операции; операции с датой устройства из будущего отвергаются с `clock_skew`; воскрешение запрещено для `card`, но `user_deck` можно вернуть; общий контент (словарь, официальные колоды) журналом не синхронизируется.

**Последствия.**
- Появляется отдельная кодовая задача (условно T1.5a): миграция 002 (`card.status`, `card.merged_into_card_id`), разделение `CardCreate` / `CardPatch`, `rejected[]` и `serverSchemaVersion` в ответе push, `z.uuid()` / `z.iso.datetime()`, типы `*Stored` с `fieldRevisions` и правка мапперов, которые сейчас стирают `field_meta`. Полный список — раздел «Код-долг» в `docs/sync-protocol.md`.
- Сессия перестаёт порождать операции по карточке: в горячем пути остаётся одна вставка в журнал.
- Симуляционные тесты недели 11 проверяют явные правила: список сценариев расширен с 6 до 12 (дубли, сдвиг часов, порядок применения, курсор, отказы, идемпотентность применения).
- `schemaVersion` операций планируется оставить равной 1 на всю бету.

**Связано.** ADR-3, ADR-4, ADR-13, T1.5, FR-27, FR-39, FR-21.
