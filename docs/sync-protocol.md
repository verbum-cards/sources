# Протокол синхронизации (черновик v0)

Статус: черновик для недели 1. Перед реализацией — ревью владельцем продукта; изменения фиксируются в `decisions.md`.

## Принципы

- Устройство — источник истины для своих изменений; сервер хранит и раздаёт журнал.
- Идентификаторы создаёт клиент: UUID v7.
- Каждое изменение — операция с уникальным `op_id`; сервер применяет её не более одного раза.
- Ответы на повторения (`review_log`) только добавляются и никогда не конфликтуют.
- Удаление — пометка `deleted_at` (tombstone), не стирание. Физическое удаление — только при удалении аккаунта.

## Операция

```ts
type SyncOp = {
  op_id: string;          // UUID v7, уникален глобально
  schema_version: number; // версия формата операции
  device_id: string;
  user_id: string;
  entity: "card" | "review_log" | "user_profile" | "user_deck";
  entity_id: string;
  kind: "upsert" | "delete";
  fields?: Record<string, unknown>; // только изменённые поля
  client_ts: string;      // ISO, время на устройстве
};
```

## Обмен

- `POST /sync/push { device_id, ops[] }` → `{ accepted: op_id[], cursor }`. Повтор уже принятой операции возвращает её в `accepted` без повторного применения.
- `GET /sync/pull?cursor=N&limit=500` → `{ ops[], next_cursor, has_more }`. Сервер присваивает каждой принятой операции монотонный `server_seq`; курсор — последний полученный `server_seq`.
- Порядок цикла на клиенте: push всех неотправленных → pull до `has_more = false` → применение локально.
- Когда: при запуске, при сворачивании, после сессии, раз в несколько минут при активной работе, при появлении сети.

## Конфликты

- Поля `card` и `user_profile`: побеждает последняя правка по паре (`client_ts`, `device_id`) — сравнение по полю, а не по записи целиком.
- `review_log`: конфликтов нет, объединение множеств.
- Удаление побеждает изменение, если `deleted_at` новее правки.

## Объединение аккаунтов (FR-39)

Первая сессия идёт до входа под временным локальным `user_id`. После входа:
- если аккаунт новый — все локальные данные перепривязываются к серверному `user_id` и отправляются как операции;
- если у аккаунта уже есть данные — две карточки с одинаковым `item_id` сливаются: остаётся более ранняя, журналы повторений объединяются, FSRS пересчитывается.

## Версии формата

Клиент отправляет `schema_version`. Сервер принимает операции старых версий и приводит их к текущей; операции новее своей версии сервер откладывает и сообщает клиенту о необходимости обновить сервер (не клиент).

## Обязательные тесты

- Симуляция: два устройства делают случайные изменения офлайн в случайном порядке, затем синхронизируются — итоговое состояние на обоих одинаковое.
- Повторная отправка той же пачки операций не меняет состояние.
- Удаление на одном устройстве не «воскрешает» карточку после синхронизации со старым.
- Обрыв связи посреди push/pull не приводит к потере или дублированию.

## Запасной план

Если к концу недели 7 синхронизация нестабильна — бета стартует с резервной копией для одного устройства (push без pull с других устройств), мультиустройство — к публичному релизу.
