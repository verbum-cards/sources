# Протокол синхронизации (v1)

Статус: согласован владельцем продукта после ревью T1.5 (см. ADR-14). Версия формата операций — `SYNC_SCHEMA_VERSION = 1` в `@cards/contracts`. Изменения — только через план архитектора и в том же PR, что и код.

Типы и схемы — `packages/contracts/src/sync.ts` и `packages/contracts/src/user.ts`. Локальные таблицы — `apps/mobile/src/db/migrations`. Модель данных — `docs/data-model.md`.

## Принципы

- Устройство — источник истины для своих изменений; сервер хранит и раздаёт журнал операций.
- Идентификаторы создаёт клиент: UUID v7.
- Каждое изменение — операция с уникальным `opId`; сервер применяет её не более одного раза.
- Ответы на повторения (`review_log`) только добавляются и никогда не конфликтуют.
- Удаление — пометка `deletedAt` (надгробие), не стирание. Физическое удаление — только при удалении аккаунта (FR-27).
- Журналом синхронизируется **только то, что принадлежит одному `userId`**. Общий контент (словарь, официальные колоды) доставляется пакетом словаря и каталогом API, а не журналом.

## Устройство

- `deviceId` — UUID v7, генерируется при первом запуске и хранится в `app_meta.device_id`. Это **не** аппаратный идентификатор: привязка к железу не нужна и вредна для приватности.
- `deviceId` участвует в разрешении конфликтов (см. «Конфликты»), поэтому обязан быть стабилен в пределах установки.
- Переустановка приложения = новый `deviceId` и `cursor = 0`, то есть полное воспроизведение журнала с сервера. Это штатный путь восстановления.
- Токены входа — в `expo-secure-store`, не в `app_meta` и не в базе.

## Что синхронизируется, а что нет

| Сущность / данные | Синхронизируется | Комментарий |
|---|---|---|
| `user_profile` | да | Одна запись на пользователя |
| `card` | да | Только пользовательские поля, см. ниже |
| `review_log` | да, только добавление | `opId` = `review_log.id` |
| `user_deck` | да | Ссылка пользователя на колоду |
| `card.status` (`active` / `suspended` / `known`) | да | Намерение пользователя: отложить, «уже знаю», вернуть в работу |
| Фаза обучения (`new` / `learning` / `review`) | **нет** | Производное от `card_schedule` и журнала; планировщик не порождает операций |
| `card_schedule` (FSRS: `due`, `stability`, `difficulty`…) | **нет** | Кеш, пересчитывается из `review_log` |
| `card_content` (снимок контента карточки) | **нет** | Локальный кеш, заполняется из пакета словаря или API редких слов |
| `sync_op`, `app_meta` | **нет** | Локальная очередь и метаданные устройства |
| `updatedAt` записи | **нет** | Производное: `max(ts)` по полям записи |
| `deck`, `deck_item`, словарь | **нет** | Общий контент: пакет словаря и каталог API |

Отсюда правило для клиента: **операцию по карточке порождают только действия пользователя** — добавление, личная правка (`overrides`), «отложить», «уже знаю», возврат в работу, удаление, слияние дублей. Ответ в сессии порождает только запись `review_log`; изменение интервала, фазы и `due` не порождает ничего.

### Колоды

- В бете существуют только колоды `type = 'official'`; они едут в пакете словаря и в каталоге API.
- `card.sourceDeckId` может ссылаться на колоду, которой на принимающем устройстве нет (другой пакет словаря). Это не ошибка: внешнего ключа нет ни в SQL, ни на сервере, интерфейс показывает карточку без источника.
- Когда появятся колоды `user` и `shared` (v1, вне беты), они становятся **новой парой сущностей синхронизации** `deck` + `deck_item` с `userId` владельца и собственным `schemaVersion`. Публикация (`shared`) — серверная операция: она делает неизменяемый снимок с новым `id` и уводит его в каталог; из журнала владельца копия больше не меняется.

## Операция

Формат на проводе — **camelCase, ровно как в `@cards/contracts`** (`SyncOpTyped`): `opId`, `schemaVersion`, `deviceId`, `userId`, `entity`, `entityId`, `kind`, `fields`, `clientTs`. Схема — размеченное объединение по `entity`, поэтому набор допустимых полей у каждой сущности проверяется валидатором, а не соглашением.

```ts
// packages/contracts/src/sync.ts — источник правды
type SyncOpTyped =
  | { entity: 'card';         kind: 'create' | 'upsert' | 'delete'; fields: CardCreate | CardPatch | null; ... }
  | { entity: 'review_log';   kind: 'create';                       fields: ReviewLogPayload;             ... }
  | { entity: 'user_profile'; kind: 'create' | 'upsert';             fields: UserProfilePatch;             ... }
  | { entity: 'user_deck';    kind: 'create' | 'upsert' | 'delete';  fields: UserDeckPatch | null;         ... }
```

### `entityId` по сущностям

| Сущность | `entityId` | Ключ на сервере |
|---|---|---|
| `card` | `card.id` (UUID v7, создаёт клиент) | `(userId, id)` |
| `review_log` | `review_log.id` (он же `opId`) | `(userId, id)` |
| `user_profile` | `userId` | `(userId)` |
| `user_deck` | `deckId` | `(userId, deckId)` |

`entityId` уникален в пределах `userId`. У `user_deck` он равен `deckId` намеренно: два устройства, добавившие офлайн одну колоду, порождают операции с одной целью и сходятся без слияния. Для `card` `entityId` — всегда собственный `id` карточки, а не `itemId`.

### Виды операций

- **`create`** — первое появление записи. Несёт **полный набор обязательных полей**: «только изменённые поля» для создания не работает, у принимающей стороны обязательные колонки `NOT NULL`.
- **`upsert`** — частичный патч: только изменённые поля. Применяется по полю (см. «Конфликты»).
- **`delete`** — `fields` отсутствует (`null`); применение ставит `deletedAt = clientTs`. Отдельного поля `deletedAt` в патчах нет, чтобы не было двух путей для одного действия.

Неизменяемые после создания поля карточки: `userId`, `itemType`, `itemId`, `createdAt`. Их изменение в `upsert` игнорируется приёмником (и клиентом, и сервером) — иначе патч мог бы подменить личность карточки.

Применение не зависит от порядка, поэтому:

- `upsert` на неизвестную запись не роняет применение: если обязательные поля в нём есть — запись создаётся по ним; если нет — операция откладывается в карантин, причина пишется в лог, остальная пачка применяется.
- `create` для уже существующей записи применяется как `upsert`: неизменяемые поля (`itemType`, `itemId`, `createdAt`) игнорируются, остальные разрешаются по полю. Так поздно пришедший `create` не может переопределить личность карточки, созданной ранее применённым `upsert`.

### `review_log`

- Допустим только `kind = 'create'`. `delete` отвергается с причиной `review_log_immutable`; единственное физическое удаление журнала — удаление аккаунта (FR-27).
- `opId = entityId = review_log.id`, поэтому повторная отправка идемпотентна без дополнительных таблиц: применение — `INSERT OR IGNORE`.
- Устройство отправляет только собственные записи журнала. Запись, пришедшая через pull, сразу помечается локально как синхронизированная, чтобы не уехать обратно.

## Авторизация

- Сервер выводит `userId` из токена доступа. Операция, у которой `userId` не совпадает с владельцем токена, отвергается с причиной `foreign_user` и не применяется; `userId` в теле операции нужен только для проверки целостности и отладки.
- До входа первая сессия идёт под локальным `userId` и **ни одна операция не отправляется** — токена нет. Это условие держит идемпотентность `opId = review_log.id` при перепривязке (см. «Объединение аккаунтов»).

## Обмен

### push

`POST /sync/push` → `{ deviceId, ops[] }`

Ответ: `{ accepted: opId[], rejected: { opId, reason, retryable }[], serverSchemaVersion, serverSeqMax }`

- Повтор уже принятой операции возвращается в `accepted` без повторного применения — push безопасно повторять после обрыва или таймаута.
- **Ответ на push не содержит курсора.** Курсор двигает только pull: иначе клиент перескочил бы операции других устройств с меньшим `serverSeq` и молча потерял бы их. `serverSeqMax` — диагностика, курсором не является.
- Максимум 500 операций в пачке.

Причины отказа:

| `reason` | `retryable` | Когда |
|---|---|---|
| `invalid_payload` | нет | Не прошло валидацию схемы |
| `foreign_user` | нет | `userId` не совпадает с владельцем токена |
| `review_log_immutable` | нет | `kind = delete` для журнала повторений |
| `account_deleted` | нет | Аккаунт удалён (FR-27) |
| `schema_too_new` | да | `schemaVersion` выше поддерживаемой сервером |
| `clock_skew` | да | `clientTs` из будущего (см. «Часы устройства») |
| `rate_limited` | да | Слишком частые запросы |

Клиент: `retryable = false` → операция снимается с очереди (помечается подтверждённой) и пишется событие в аналитику; `retryable = true` → повтор с возрастающей задержкой, очередь не теряется и не блокируется другими операциями.

### pull

`GET /sync/pull?cursor=N&limit=500` → `{ ops: (SyncOpTyped & { serverSeq })[], nextCursor, hasMore }`

- Сервер присваивает каждой принятой операции монотонный `serverSeq` в порядке приёма; курсор — последний **применённый** `serverSeq`. Курсор хранит клиент (`app_meta.sync_cursor`); сервер может хранить копию только для диагностики.
- Pull возвращает **все** операции пользователя, включая собственные операции запрашивающего устройства. Фильтровать по `deviceId` не нужно: применение своих операций — пустая операция по правилу «равные `(clientTs, deviceId)` не новее», а устройство, потерявшее локальную базу, получает свою историю обратно.
- **Применение пачки и запись нового курсора — в одной транзакции.** Отдельной таблицы применённых `opId` не нужно: применение идемпотентно (`INSERT OR IGNORE` для журнала, сравнение по полю для остальных), поэтому повтор пачки после обрыва безопасен.

### Цикл и расписание

- Порядок: push всех неотправленных → pull до `hasMore = false` → применение.
- Когда: при запуске, при сворачивании, после сессии, раз в несколько минут при активной работе, при появлении сети.
- Не чаще раза в минуту; при ошибках сети и `retryable` отказах — экспоненциальная задержка; без сети попыток нет.

### Первичная синхронизация и компакция

- Новое устройство (или переустановка) делает pull с `cursor = 0` и воспроизводит журнал целиком. При 5 000 повторений это порядка 1 МБ — для беты приемлемо.
- Компакция журнала (свернуть операции `card`, `user_profile`, `user_deck` до последнего значения каждого поля) — после беты. Журнал повторений компактить нельзя. Любая компакция обязана сохранить `(clientTs, deviceId)` каждого поля, иначе разрешение конфликтов на устройствах разъедется.

## Часы устройства

`clientTs` — время устройства, и оно же решает конфликты. Телефон с датой на год вперёд выиграл бы все конфликты навсегда.

- Сервер ставит собственную метку `serverReceivedAt` (для диагностики и `serverSeq`).
- Операции с `clientTs > serverNow + 15 минут` отвергаются с `reason = clock_skew, retryable = true`. Клиент показывает «проверьте дату и время на устройстве» и повторяет позже; очередь не теряется.
- Небольшой сдвиг принимается как есть: на разрешение конфликтов он влияет не сильнее реальной одновременности.
- Сервер **не исправляет** `clientTs` молча: значение, по которому применяют другие устройства, обязано совпадать с тем, что хранит источник в своих метаданных полей, иначе источник и остальные разойдутся при следующем конфликте.

## Конфликты

Разрешение — «последняя правка побеждает» **по полю**, а не по записи целиком. Для этого у `card`, `user_profile` и `user_deck` хранятся метаданные правок (`field_revisions`, тип `FieldRevisions` в `@cards/contracts`; в SQL — колонка `field_meta`). Это метаданные, а не синхронизируемое поле: они выводятся из операций и через журнал не едут.

Алгоритм одинаков на клиенте и на сервере:

```
для каждого поля f из op.fields (плоские ключи: overrides.translation и т. п.):
  local    = fieldRevisions[f]                              // { ts, deviceId } или отсутствует
  incoming = { ts: op.clientTs, deviceId: op.deviceId }
  применить, если local отсутствует
             ИЛИ incoming.ts > local.ts
             ИЛИ (incoming.ts == local.ts И incoming.deviceId > local.deviceId)
  при применении: записать значение и fieldRevisions[f] = incoming

ts сравниваются как строки ISO-8601 UTC с Z (лексикографический порядок = хронологический);
deviceId — лексикографически по байтам.
Равные (ts, deviceId) → «не новее» → пропустить: поэтому применение собственных
операций, вернувшихся через pull, безопасно.
updatedAt записи = max(ts) по её полям — производное, не синхронизируется.
```

### Личные правки (`overrides`)

- Операция может нести **частичный** объект `overrides`; он применяется по ключам. Ключи метаданных — плоские: `overrides.translation`, `overrides.example`, `overrides.note`.
- Отсутствующий ключ = «не менялось». Чтобы **стереть** правку, передаётся `null` (то же правило для `sourceDeckId`): в JSON «отсутствует» и «стёрто» иначе неразличимы.

### `review_log`

Конфликтов нет: объединение множеств по `id`.

### Удаление

- Для `card` удаление необратимо: воскрешение карточки — критическая ошибка. Пользователь, добавивший ранее удалённое слово, получает **новую** карточку с новым `id` и чистой историей.
- Для `user_deck` `deletedAt` — обычное поле с разрешением по правилу выше: «убрал колоду → добавил снова» выражается операцией `upsert` с `deletedAt = null`. Иначе колоду нельзя было бы вернуть, потому что `entityId = deckId` не меняется.
- Удаление побеждает более раннюю правку: правки полей с `ts` старше `deletedAt` игнорируются.
- Удаление карточки **не** удаляет её записи журнала ни локально, ни на сервере.

### Дубли карточек

Инвариант: одна **живая** карточка на `(userId, itemType, itemId)`. Добавление слова из колоды, когда карточка уже есть, не создаёт вторую — оно лишь проставляет `sourceDeckId`, если тот был пуст. Уникального индекса в SQL нет намеренно: иначе входящая операция с другого устройства не применилась бы; инвариант держится правилом слияния.

Правило слияния — одно и то же для «два устройства добавили офлайн одно значение» и для объединения аккаунтов:

1. Среди живых карточек с одинаковым `(userId, itemType, itemId)` побеждает **меньший `id`**. UUID v7 монотонен, значит это и есть более ранняя карточка; правило детерминировано и не зависит от `createdAt`, который сам может конфликтовать.
2. Проигравшая получает `deletedAt` и `mergedIntoCardId = id` победителя.
3. Журнал повторений не трогаем (он неизменяем). FSRS победителя считается по записям всех карточек, чьё `mergedIntoCardId` ведёт к нему транзитивно.
4. Слияние идемпотентно: повторное применение даёт тот же результат на всех устройствах.
5. Удалённые карточки в слиянии не участвуют.

## Объединение аккаунтов (FR-39)

Первая сессия идёт до входа под временным локальным `userId`; операции при этом не отправляются (нет токена). После входа:

1. Перепривязка — **одна транзакция**: `userId` в `user_profile`, `card`, `review_log`, `user_deck`; `userId` в `sync_op` (колонка и внутри `fields`, если он там есть); `entityId` операций по `user_profile` (он равен `userId`); затем `app_meta.user_id_is_local = '0'`.
2. Локальные данные отправляются как операции обычным циклом.
3. Карточки с одинаковым `(itemType, itemId)` сливаются по общему правилу дублей — отдельного правила для объединения аккаунтов нет.
4. **Профиль: побеждает локальный целиком.** Клиент отправляет одну операцию `user_profile` со **всем** набором полей и `clientTs` = время входа. Пользователь только что прошёл онбординг на этом устройстве, поэтому его ответы новее любых серверных и побеждают по обычному правилу «по полю». Разрешение по полю здесь не годится: смесь «родной язык с одного устройства, изучаемый с другого» бессмысленна. Крайний случай — на сервере лежит правка с более поздней меткой (сдвинутые часы другого устройства); тогда побеждает она, и это допустимо.

## Удаление аккаунта (FR-27)

- После удаления сервер отвергает все операции устройств этого пользователя с `reason = account_deleted, retryable = false`.
- Клиент по этой причине стирает `cards-user.db`, сбрасывает `deviceId` и курсор. Подтверждение у пользователя уже получено на экране удаления; при обычном выходе из аккаунта локальная база удаляется только с отдельным подтверждением (ADR-13).
- Удаление аккаунта — единственный случай физического удаления пользовательских данных, включая журнал повторений.

## Версии формата

- Клиент отправляет `schemaVersion` (`SYNC_SCHEMA_VERSION` из `@cards/contracts`).
- Сервер принимает операции **старых** версий и приводит их к текущей.
- Операцию с версией **выше** поддерживаемой сервер не сохраняет, а отвергает с `schema_too_new, retryable = true` и возвращает `serverSchemaVersion`. Хранить непонятую операцию в журнале нельзя: pull раздал бы её другим устройствам. Клиент держит такие операции в очереди до обновления сервера и сообщает об этом в диагностике.

## Порядок применения и согласованность

Применение обязано быть независимым от порядка: операции из разных пачек получают разный `serverSeq`, и запись журнала может прийти раньше своей карточки.

- Запись `review_log` вставляется всегда, даже если `cardId` ещё неизвестен. FSRS для такой карточки считается, когда придёт сама карточка.
- Запись журнала, пришедшая после удаления карточки, принимается: журнал неизменяем и карточку не воскрешает.
- Записи журнала удалённой карточки существуют, но в планировании не участвуют.
- После применения операции по карточке снимок `card_content` на этом устройстве пуст (снимок не синхронизируется, ADR-13). Устройство ставит задачу заполнить его из пакета словаря или через API редких слов по `(itemType, itemId)`. До заполнения карточка в сессию не выдаётся.

## Обязательные тесты

Стенд: сервер sync поверх тестовой базы и N «устройств» — клиентов с отдельными локальными базами в памяти. Зерно генератора случайных чисел фиксировано; при падении выводятся зерно и минимальная последовательность операций.

1. **Сходимость.** 2–3 устройства делают случайные операции офлайн, синхронизируются в случайном порядке и повторно → состояния всех устройств и сервера совпадают.
2. **Идемпотентность push.** Повтор той же пачки не меняет состояние.
3. **Обрывы.** Прерывание после отправки до получения ответа и посреди pull → нет потерь и дублей.
4. **Удаления.** Удаление на устройстве A, более старая правка на устройстве B → карточка остаётся удалённой.
5. **Старый клиент.** Операции предыдущей `schemaVersion` принимаются и приводятся; операция с версией новее сервера отвергается и остаётся в очереди.
6. **Объединение аккаунтов.** Локальная первая сессия плюс существующий аккаунт с пересекающимися карточками; профиль побеждает локальный целиком.
7. **Дубли.** Два устройства офлайн добавляют одно и то же значение → после синхронизации ровно одна живая карточка, история повторений обеих учтена планировщиком через `mergedIntoCardId`.
8. **Сдвиг часов.** Устройство с датой на год вперёд → операции отвергнуты с `clock_skew`, очередь не потеряна, чужие поля не затёрты.
9. **Порядок применения.** Запись журнала применяется раньше своей карточки и после её удаления → нет падений, нет воскрешения, FSRS сходится.
10. **Курсор.** После push клиент не двигает курсор; операции третьего устройства с меньшим `serverSeq` не теряются.
11. **Отказы.** Операция с `retryable = false` снимается с очереди и не блокирует остальные; с `retryable = true` — остаётся и уходит после восстановления.
12. **Идемпотентность применения.** Повтор той же пачки pull (обрыв до записи курсора) не меняет состояние.

## Запасной план

Если к концу недели 7 синхронизация нестабильна — бета стартует в режиме «резервная копия для одного устройства»: `syncMode = 'backup_only'`, push работает, применение pull выключено. Это **флаг**, а не отдельная ветка кода. Мультиустройство — к публичному релизу.
