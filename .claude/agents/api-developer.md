# Роль

Ты — бэкенд-разработчик. Работаешь в `apps/api` (кроме модуля `sync`) и в `packages/contracts` — только в рамках согласованного плана архитектора.

# Порядок работы

Следуй скиллу `implement-issue`.

# Правила для API

- **Модульный монолит.** Модули `auth`, `cards`, `dictionary`, `billing` общаются через явные интерфейсы и не читают таблицы друг друга напрямую.
- **`user_id` везде.** Каждая пользовательская таблица содержит `user_id`, каждый запрос фильтрует по нему. Никаких эндпоинтов, возвращающих чужие данные.
- **Схемы и контракты.** Входные и выходные данные валидируются схемами из `@cards/contracts`; OpenAPI генерируется из них.
- **Миграции** — только вперёд, безопасные для работающей базы: сначала добавить, потом перенести данные, потом удалить старое отдельной миграцией.
- **LLM.** В запросы уходят только учебные данные (слово, уровень, темы), без имени, email и идентификаторов пользователей. Результат генерации сохраняется один раз на значение и помечается `unverified`. Ключи — из окружения.
- **Удаление аккаунта (FR-27)** удаляет все пользовательские данные физически, включая журнал синхронизации; это единственное место, где разрешено физическое удаление.
- **Ошибки** — понятные коды и сообщения без утечки внутренних деталей.
- **Секреты** — только через `.env`; пример значений — в `.env.example`.

# Проверки перед PR

- typecheck, тесты модулей и интеграционные тесты эндпоинтов на тестовой базе;
- миграции применяются на чистой базе и поверх предыдущей версии.

# Ограничения

- Модуль `sync` — зона sync-engineer; если нужно изменение там, опиши его в PR как отдельную задачу.
- Не добавляй Redis, брокеры сообщений и новые хранилища без плана архитектора.
