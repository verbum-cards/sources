# Ревью PR

## 0. Когда не ревьюить

Пропусти черновики и закрытые PR. Если у PR уже есть твой итоговый комментарий (первая строка `<!-- review -->`) и новых коммитов после него нет — не повторяй ревью.

## 1. Контекст

```bash
gh pr view $PR --json number,title,body,files,commits,labels,headRefName
gh pr diff $PR
```

Найди связанный issue (`Closes #N`), прочитай его, комментарии разбора (`<!-- triage -->`), плана (`<!-- plan -->`) и архитектора (`<!-- design -->`).

## 2. Соответствие задаче

- Каждый критерий приёмки — выполнен, частично, не выполнен. Проверяй по коду и тестам, а не по отметкам в описании PR.
- Нет ли изменений вне области задачи.
- Если был план архитектора — реализация ему следует; отклонения объяснены.

## 3. Правила проекта (быстрые проверки)

```bash
# hex-цвета в коде приложений (допустимы только в packages/tokens)
git diff origin/main...HEAD -- 'apps/**/*.ts' 'apps/**/*.tsx' 'apps/**/*.css' | grep -nE '^\+.*#[0-9a-fA-F]{3,8}\b'
# кириллица в JSX/TSX мимо i18n
git diff origin/main...HEAD -- 'apps/**/*.tsx' | grep -nE '^\+.*>[^<{]*[А-Яа-яЁё]'
# похожее на секреты
git diff origin/main...HEAD | grep -nEi '^\+.*(api[_-]?key|secret|token|password)\s*[:=]\s*["'"'"'][^"'"'"']{8,}'
```

Находки — повод посмотреть внимательно, а не автоматическая ошибка.

Проверь по смыслу:
- **Local-first:** действие пользователя не ждёт сети; офлайн-сценарий не сломан.
- **Модель данных:** карточка ссылается на sense/expression; уровень у значения; `user_id` у пользовательских данных; идентификаторы — UUID v7 на клиенте.
- **API:** каждый запрос к пользовательским данным фильтруется по `user_id`; входные данные валидируются схемами из `@cards/contracts`.
- **Контракты:** общие типы не продублированы в приложениях.
- **Миграции:** безопасны для существующих данных, только вперёд.
- **Синхронизация:** идемпотентность, отсутствие «воскрешения» удалённого, тесты-симуляции (если затронута).
- **LLM:** в запросах нет личных данных.
- **Доступность:** роли и подписи у интерактивных элементов, зоны нажатия ≥ 44 pt, «Уменьшить движение».
- **Производительность:** нет тяжёлой работы на критическом пути (старт, поиск, переход между карточками).
- **Требования магазинов** (скилл `store-compliance`), если PR касается сбора данных, входа, разрешений, удаления аккаунта или оплат.
- **Документы** обновлены, если поменялось поведение или модель.

## 4. Тесты

Для логики тесты обязательны. Хороший тест проверяет поведение из критериев приёмки и граничные случаи, а не повторяет реализацию. Нет тестов на новую логику — это «нужны правки».

## 5. Комментарии

- Конкретные замечания — инлайн к строкам (инструмент `mcp__github_inline_comment__create_inline_comment`), каждое с уровнем: **Критично** (данные, безопасность, критерии), **Важно** (правила проекта, тесты), **Можно лучше** (необязательно).
- Итог — один комментарий в PR (`gh pr comment`), первая строка `<!-- review -->`; при повторном ревью обнови его через `gh api`, а не пиши новый.

```markdown
<!-- review -->
**Ревью**

**Критерии приёмки**
- [x] …
- [ ] … — не выполнено: …

**Замечания:** критичных — N, важных — N, необязательных — N (подробности — в комментариях к строкам).

**Что сделано хорошо:** …

**Вердикт:** можно вливать после проверки на телефоне | нужны правки | нужно решение владельца: …
```

## Ограничения

Не одобряй PR через механизм review GitHub, не вливай, не пушь. Не требуй изменений вне задачи — предлагай отдельные issues.
