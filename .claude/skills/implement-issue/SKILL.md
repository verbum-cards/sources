# Реализация issue

## 1. Проверить, можно ли начинать

```bash
gh issue view $ISSUE --json number,title,body,labels,comments,milestone
```

Начинать можно, только если одновременно:
- есть метки `ready` и `triage:done`;
- нет `needs-info`, `needs-design`, `blocked`, `later`;
- если задача проходила через архитектора — в комментариях есть план `<!-- design -->`.

Если условие не выполнено — оставь комментарий, чего не хватает, и остановись.

## 2. Выбрать исполнителя

| Метка | Агент |
|---|---|
| `area:mobile` | mobile-developer |
| `area:api` | api-developer |
| `area:sync` | sync-engineer |
| `area:web`, `area:backoffice` | web-developer |
| `area:content` | content-engineer |
| `area:docs` | выполни сам |

Если запущен как основной агент — делегируй задачу нужному агенту, передав номер issue, текст, комментарий разбора, план архитектора и эти инструкции. Если ты уже этот агент — продолжай.

## 3. План комментарием

До кода опубликуй в issue комментарий с первой строкой `<!-- plan -->`: какие файлы изменишь, какие тесты добавишь, как проверишь каждый критерий приёмки. Короче плана архитектора — 5–15 строк. Если по ходу план меняется — обнови комментарий.

## 4. Ветка

```bash
git checkout -b issue-$ISSUE-<короткое-описание-латиницей>
```

## 5. Реализация

- Работай только в своей области (см. файл агента). Нужны изменения вне её — не делай, а опиши в PR как предложение отдельной задачи.
- Маленькие коммиты, каждый — рабочее состояние. Сообщения на английском в формате `type(area): описание (#N)`, например `feat(mobile): daily new-card limit (#42)`. Типы: feat, fix, test, refactor, docs, chore.
- Логика — с тестами: планировщик, очереди, синхронизация, нормализация, валидация, миграции.
- Если поведение или модель данных изменились — обнови документы в `docs/` в том же PR. Новое решение — запись по скиллу `write-adr`.

## 6. Проверки

```bash
pnpm install --frozen-lockfile
pnpm -r typecheck
pnpm -r test --if-present
```

Если чего-то нет (проект ещё не настроен) — отметь в PR, что не проверено и почему. Не отключай проверки и тесты, чтобы они прошли.

## 7. Pull request

```bash
git push -u origin HEAD
gh pr create --title "<тип>(<область>): <что сделано> (#$ISSUE)" --body-file <файл> --label "area:..."
```

Тело PR — по шаблону `.github/pull_request_template.md`:
- `Closes #N`;
- что сделано и почему так (2–5 пунктов);
- чек-лист критериев приёмки с отметками;
- как проверить на телефоне — шаги из issue, уточнённые по факту;
- что проверено автоматически и что требует ручной проверки владельцем;
- отклонения от плана и предложения отдельных задач.

## 8. Если застрял

Неясность в требованиях, противоречие документам, задача оказалась крупнее или требует решения архитектора — не угадывай. Закоммить то, что уже рабочее, в ветку без PR, оставь в issue комментарий с конкретным вопросом (первая строка `<!-- implement -->`), поставь `needs-info` (или `needs-design`) и остановись.

## Ограничения

- Не вливай PR и не делай push в основную ветку.
- Не ставь и не снимай метки `ready`, `needs-design`.
- Не добавляй зависимости без упоминания в PR; крупные — только по плану архитектора.
- Никаких секретов в коде, логах и PR.
