# Разбор issue

Цель: задача, которая получает `triage:done`, должна быть понятной разработчику без вопросов, проверяемой и соответствовать документам проекта. Ты не решаешь, брать ли её в работу, — это делает владелец продукта меткой `ready`.

## 0. Загрузить контекст

```bash
gh issue view $ISSUE --json number,title,body,labels,milestone,comments,author
```

Прочитай документы, которые относятся к задаче: `docs/requirements-beta.md`, `docs/product.md` (объём беты), нужные разделы `docs/flows.md`, `docs/data-model.md`, `docs/sync-protocol.md`, `docs/design-system.md`, `docs/decisions.md`. Не полагайся на память — документы меняются.

Проверь дубликаты:

```bash
gh issue list --state all --search "<ключевые слова> in:title,body" --limit 10
```

Если это дубликат — комментарий со ссылкой на основной issue, метка `duplicate`, закрыть (`gh issue close $ISSUE --reason "not planned"`). Дальше не разбирать.

## 1. Переразбор или первый разбор

У каждого issue — **один** комментарий разбора, помеченный первой строкой `<!-- triage -->`. Найди его:

```bash
gh api repos/{owner}/{repo}/issues/$ISSUE/comments --jq '.[] | select(.body | startswith("<!-- triage -->")) | .id'
```

- Нет комментария — создай новый (`gh issue comment`).
- Есть — обнови его (`gh api -X PATCH repos/{owner}/{repo}/issues/comments/<id> -f body=...`), а не пиши второй. Если владелец ответил на вопросы — сними `needs-info` и разбери заново с учётом ответов.

## 2. Проверить объём

Сверь задачу с `docs/product.md` → «Объём беты» и «Не входит в бету».

- Входит в бету → продолжай.
- Относится к более позднему этапу → метка `later`, milestone не ставь, в комментарии — к какому этапу относится (публичный релиз, v1, v2) и почему. Дальше не готовь к работе.
- Противоречит документам (например, требует hex-цвета, нарушает local-first, ставит уровень на слово, а не на значение) → опиши противоречие, `needs-info`. Не переписывай задачу молча.

## 3. Определить тип и область

**Тип:** `type:feature`, `type:bug`, `type:content` (словарь и колоды, чаще работа редактора), `type:chore` (инфраструктура, зависимости, CI), `type:owner` (задачи человека: аккаунты, юристы, найм — не идут в разработку).

**Область:** ровно одна из `area:mobile`, `area:api`, `area:sync`, `area:web`, `area:backoffice`, `area:content`, `area:docs`. Синхронизация — исключение: клиент и сервер синхронизации — одна область `area:sync`. Если задача затрагивает две другие области — дроби (шаг 6).

## 4. Размер

| Размер | Признаки |
|---|---|
| `size:S` | Одна область, до ~3 файлов, без новых сущностей данных; например, текст, стиль, одна функция с тестами |
| `size:M` | Один экран, один эндпоинт или один модуль; новые компоненты; тесты; до 1–2 дней |
| `size:L` | Несколько экранов или областей, новая сущность данных вместе с UI, размытые требования — **дробить обязательно** |

При сомнении между M и L — выбирай L и дроби: маленькие PR ревьюятся лучше.

## 5. Нужен ли план архитектора

Ставь `needs-design`, если задача:

- меняет модель данных (новая таблица, поле общей сущности, миграция пользовательских данных);
- трогает протокол синхронизации или `packages/contracts`;
- добавляет нативный модуль, ORM, менеджер состояния или другую крупную зависимость;
- касается входа, безопасности, удаления пользовательских данных;
- чувствительна к скорости по бюджетам (поиск по словарю, холодный старт, переход между карточками).

`needs-design` не мешает остальному разбору: заполни всё, что можешь, и отметь, что решение ждёт плана.

## 6. Дробление (для size:L и задач на две области)

- Каждая подзадача — одна область, размер S или M, самостоятельная польза или проверяемый шаг.
- Порядок: сначала данные и контракты, потом API, потом клиент.
- Создай подзадачи и свяжи с исходной:

```bash
gh issue create --title "<ID>.<n> <название>" --body "Part of #$ISSUE ..." --label "area:...,type:...,size:..." --milestone "Неделя NN"
```

- Исходную задачу оставь открытой как «зонтик» с чек-листом подзадач в комментарии разбора; `triage:done` на зонтик не ставь.

## 7. Для багов — дополнительно

Нужны: шаги воспроизведения, ожидаемое и фактическое поведение, устройство и ОС, версия сборки. Чего нет — спроси (`needs-info`).

Если есть риск потери или порчи пользовательских данных, неверной синхронизации или падения при запуске — `p1` и отдельной строкой «Критично» в комментарии.

## 8. Критерии приёмки и проверка

Если в issue нет проверяемых критериев — напиши их сам на основе FR и флоу:

- каждый критерий проверяется «да/нет», без слов «удобно», «быстро», «красиво» без числа;
- используй бюджеты из документов (например, превью ≤ 300 мс без сети);
- для мобильных задач — раздел «Как проверить на телефоне» по шагам, включая авиарежим и тёмную тему, если применимо;
- для задач с логикой — какие тесты должны появиться.

## 9. Приоритет и неделя

- `p1` — обязательно для беты (Must в `requirements-beta.md`, баги с потерей данных); `p2` — желательно.
- Milestone «Неделя NN» — по `docs/plan.md`. Если в задаче неделя не указана — предложи ближайшую подходящую и отметь это в комментарии.

## 10. Готовность (Definition of Ready)

Ставь `triage:done` только если всё выполнено:

- [ ] Одна область (или `area:sync`)
- [ ] Связь с FR, флоу или явная причина задачи
- [ ] Проверяемые критерии приёмки
- [ ] «Как проверить на телефоне» для мобильных задач
- [ ] Размер S или M
- [ ] Нет открытых вопросов
- [ ] Входит в текущий этап
- [ ] Зависимости закрыты или отмечены `blocked` со ссылкой

Иначе — `needs-info`, `needs-design` или `blocked` с объяснением. **Метку `ready` не ставь никогда.**

## 11. Комментарий разбора

Формат — в `references/comment-template.md`. Примеры хороших разборов — в `references/examples.md`; прочитай их при первом разборе в сессии.

Коротко: русский язык, ссылки на документы вместо пересказа, не больше трёх вопросов, последняя строка — статус и что нужно от владельца.

## 12. Метки

Создавай отсутствующие метки при первой необходимости (`gh label create`). Полный список — в `references/labels.md`.
