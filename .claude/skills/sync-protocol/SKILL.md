# Протокол синхронизации

Спецификация — `docs/sync-protocol.md`, версия v1 (источник правды; меняется только через план архитектора и в том же PR, что и код). Типы — `SyncOpTyped`, `SyncPushRequest`, `SyncPullResponse` в `packages/contracts`. Формат на проводе — camelCase, как в контрактах.

## Коротко

- Клиент пишет каждое изменение в локальный журнал операций с `opId` (UUID v7). Виды: `create` (полный набор обязательных полей), `upsert` (патч), `delete`.
- Цикл: push всех неотправленных → pull по курсору до `hasMore = false` → применение. Применение пачки и запись курсора — в одной транзакции.
- **Курсор двигает только pull.** Ответ на push курсора не содержит: иначе теряются операции других устройств.
- Сервер применяет операцию не более одного раза, присваивает монотонный `serverSeq`, берёт `userId` из токена (а не из тела операции).
- Конфликты: последняя правка по полю (`clientTs`, затем `deviceId`) через метаданные `field_revisions`; `review_log` — объединение, только `kind = 'create'`; удаление побеждает более раннюю правку.
- У карточки синхронизируется намерение `status` (`active` / `suspended` / `known`); фазы `new` / `learning` / `review`, `due` и FSRS — производные и операций не порождают.
- Удаление — `deletedAt`; воскрешение `card` — критическая ошибка (повторное добавление = новая карточка), а `user_deck` вернуть можно.
- Дубли: одна живая карточка на `(userId, itemType, itemId)`; побеждает меньший `id`, проигравшая получает `mergedIntoCardId`, журнал не переписывается.
- Объединение аккаунтов: данные первой сессии перепривязываются к `userId` после входа (до входа не отправляется ничего); профиль локального устройства побеждает целиком.

## Где код

- Клиент: `apps/mobile/src/sync/` — журнал операций, отправка, получение, применение, расписание запусков.
- Сервер: модуль `sync` в `apps/api` — приём, дедупликация по `op_id`, `server_seq`, выдача по курсору, приведение старых версий.

## Симуляционные тесты (обязательны)

Тестовый стенд: сервер sync поверх тестовой базы и N «устройств» — клиентов с отдельными локальными базами в памяти.

1. **Сходимость:** 2–3 устройства делают случайные операции (создание, правка полей, ответы, удаление) офлайн, затем синхронизируются в случайном порядке и повторно → итоговые состояния всех устройств и сервера совпадают.
2. **Идемпотентность:** повтор той же пачки push не меняет состояние.
3. **Обрывы:** прерывание после отправки до получения ответа, посреди pull → нет потерь и дублей.
4. **Удаления:** удаление на устройстве A, старая правка на устройстве B, синхронизация → карточка остаётся удалённой.
5. **Старый клиент:** операции предыдущей `schemaVersion` принимаются и приводятся; операция версии новее сервера отвергается (`schema_too_new`) и остаётся в очереди.
6. **Объединение аккаунтов:** локальная первая сессия + существующий аккаунт с пересекающимися карточками; профиль побеждает локальный целиком.
7. **Дубли:** два устройства офлайн добавляют одно значение → одна живая карточка, история обеих учтена через `mergedIntoCardId`.
8. **Сдвиг часов:** устройство с датой на год вперёд → отказ `clock_skew`, очередь не потеряна, чужие поля не затёрты.
9. **Порядок применения:** запись журнала приходит раньше своей карточки и после её удаления → нет падений и воскрешения.
10. **Курсор:** после push курсор не двигается; операции третьего устройства с меньшим `serverSeq` не теряются.
11. **Отказы:** `retryable = false` снимает операцию с очереди и не блокирует остальные; `retryable = true` уходит после восстановления.
12. **Идемпотентность применения:** повтор пачки pull (обрыв до записи курсора) не меняет состояние.

Используй фиксированное зерно генератора случайных чисел, чтобы упавший тест воспроизводился; при падении выводи зерно и минимальную последовательность операций.

## Запасной план

Если к концу недели 7 синхронизация нестабильна — режим «резервная копия для одного устройства» (push без применения чужих изменений), мультиустройство — к публичному релизу. Режим включается флагом, а не отдельным кодом.
